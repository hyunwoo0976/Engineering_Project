# 검증 방법론

테스트벤치 작성법과 검증 사고방식. DV 목표의 핵심 파일.

---

## 1. 검증의 출발점

> **"눈으로 파형 확인"은 검증이 아니다. 시뮬레이터가 판정해야 한다.**

| | 방식 | 문제 |
|---|---|---|
| ❌ | 파형을 띄워 사람이 봄 | 케이스 100개면 불가능. 코드 고칠 때마다 다시 다 봐야 함 |
| ✅ | 기대값을 코드에 박아 자동 판정 | 몇 개든 즉시 재검증 (회귀) |

파형은 **FAIL 났을 때 원인을 추적하는 도구**로 쓴다.

---

## 2. 테스트벤치 기본 구조

포트가 없는 모듈. 신호를 만들어 DUT(Device Under Test)에 꽂고 관찰한다.

```verilog
`timescale 1ns/1ps
module Xxx_tb;
    // 1) 신호 선언
    // 2) DUT 인스턴스
    // 3) task / function 정의
    initial begin
        // 4) 자극 + 판정
        $finish;
    end
endmodule
```

### reg냐 wire냐 — 가장 많이 헷갈리는 것

| 역할 | 타입 | 이유 |
|---|---|---|
| DUT **입력**에 연결 | `reg` | 내가 값을 만들어 넣음 (procedural 대입) |
| DUT **출력**에서 받음 | `wire` | DUT가 구동. 내가 대입하면 안 됨 |

> 기억법: **내가 만드는 건 `reg`, 받아보는 건 `wire`**

### 포트 연결은 이름 기반으로
```verilog
DUT u_dut( .a(a), .b(b), .y(y) );
```
순서 기반은 포트 순서가 바뀌면 **조용히 틀린다.**
그리고 **포트를 빠뜨리면 `z`(floating)** 가 되어 결과가 전부 이상해진다.

## 3. task와 function

| | task | function |
|---|---|---|
| 반환값 | 없음 | **있음** (함수 이름에 대입) |
| 시간 소모 (`#1`, `@(posedge)`) | **가능** | **불가능** |
| 호출 위치 | 문장으로 (`clr;`) | 표현식 안 (`x = f();`) |

**판단 기준 2개**
1. 시간을 써야 하나? → **task만 가능**
2. 값을 돌려받아야 하나? → **function**

### 주의사항
- 인자마다 타입을 **각각** 써야 함: `task t(input [1:0] a, input [1:0] b);`
- function은 `return`이 없다. **함수 이름에 대입**하면 그게 반환값
- 인자 없는 function은 **`-g2012` 필요** (순수 Verilog는 input 최소 1개)
- task/function 정의는 **모듈 레벨**, 호출은 `initial` 안

### 자주 쓰는 두 개

```verilog
// 초기화 — 케이스 간 값 오염 방지
task clr;
    begin
        a = 0; b = 0; sel = 0;
    end
endtask

// 판정 + 카운트
task check(input [1:0] expected, input [200:0] name);
    begin
        #1;                                   // 값 안정화
        if (out === expected) begin
            $display("[PASS] %0s", name); PASS = PASS + 1;
        end
        else begin
            $display("[FAIL] %0s | got %b expect %b", name, out, expected);
            FAIL = FAIL + 1;
        end
    end
endtask
```

케이스 하나가 **두 줄**로 줄어든다:
```verilog
clr; a = 1; b = 1;   check(2'b10, "케이스 이름");
```

## 4. `==` vs `===` ★

| 연산자 | x/z 처리 |
|---|---|
| `==` | x가 섞이면 결과가 **x** → `if`에서 거짓 취급 |
| `===` | x, z까지 **그대로 비교** |

**자동 판정엔 반드시 `===`(또는 `!==`)를 쓴다.** `==`로 하면 출력이 x인데도 조용히 넘어가는 경우가 생긴다.

## 5. 조합회로 vs 순차회로

### 조합회로 (클럭 없음)
```verilog
입력 세팅 → #1 → 확인
```
`#1`을 넣는 이유: 입력을 바꾼 그 순간엔 출력이 아직 옛값일 수 있다.

### 순차회로 (클럭 있음)
```verilog
reg clk, reset;
always #5 clk = ~clk;        // 주기 10ns

initial begin
    clk = 0;  reset = 1;     // ★ clk 초기화 필수 (x면 토글 안 됨)
    @(negedge clk); @(negedge clk);
    reset = 0;
    ...
end
```

**언제 입력을 바꾸나**
- 입력은 **`@(negedge clk)`** 에서 바꾸고, 결과는 **`@(posedge clk)` 이후** 확인
- 이유: posedge와 **같은 시각**에 입력을 바꾸면 "값을 바꾸는 일"과 "값을 읽는 일"이 동시에 일어나 **순서 보장이 안 됨**(레이스)
- 실제 하드웨어를 더 충실히 모사하려면 `@(posedge clk); #1; data = ...` (clk-to-Q 지연 모사)
- 여러 클럭 대기: `repeat(8) @(posedge clk);`

## 6. self-checking의 3요소

| 요소 | 뜻 |
|---|---|
| **stimulus (자극)** | DUT에 넣을 입력 |
| **expected (기대값)** | 사양대로면 나와야 할 출력 |
| **check (비교)** | 실제 vs 기대 자동 판정 |

### ★ 기대값은 사양에서 유도한다 — DUT에서 베끼면 안 된다

> DUT 코드를 보며 "여기서 `2'b10`이 나오네, 그럼 기대값 `2'b10`" 하면
> **DUT가 틀렸을 때 TB도 똑같이 틀린다.** 항상 PASS가 나오고, 아무것도 검증하지 않은 셈이 된다.

올바른 순서:
```
사양: 소비자가 Rs1으로 x5를 읽고, MEM 단계가 x5에 쓴다
   → Rs1은 MEM에서 포워딩되어야 한다
   → 인코딩 규약상 2'b10
따라서 기대값 = 2'b10
```
**DUT를 한 줄도 안 보고** 이 기대값이 나와야 한다.

## 7. 케이스를 빠짐없이 뽑는 방법

무작정 떠올리지 말고 **네 가지 축**으로 훑는다.

| 축 | 내용 |
|---|---|
| **① 기능** | 출력이 가질 수 있는 값마다 하나씩 |
| **② 게이팅 (negative)** | 조건을 하나씩 꺼서 "동작하면 안 되는데 하는지" 확인 |
| **③ 상호작용** | 두 조건이 동시에 성립할 때 우선순위 |
| **④ 기본 상태** | 아무 조건도 없을 때 |

**②가 버그를 제일 많이 잡는다.** "켜져야 할 때 켜지나"보다 "**꺼져야 할 때 꺼지나**"가 놓치기 쉽다.

**④는 유효한 값으로 채우되 조건만 안 맞게** 만든다. 전부 0으로 하면 우연히 통과할 수 있어 약한 테스트가 된다.

## 8. constrained random

케이스가 수십 개를 넘어가면 손으로 다 못 짠다. 랜덤 입력 + 참조 모델로 넘어간다.

```verilog
repeat(1000) begin
    clr;
    // 랜덤 입력 (제약 걸어서)
    ...
    #1;
    exp = ref_model();                   // 참조 모델이 정답 계산
    if ({out} !== exp) begin FAIL = FAIL+1; $display("FAIL ... 입력=%b", 입력); end
    else PASS = PASS+1;
end
```

**directed와 달리 기대값을 하드코딩할 수 없다.** 대신 **기대값을 만드는 규칙**(참조 모델)을 한 번 쓴다.

### 왜 "제약(constrained)"인가

주소를 0~31 전 범위로 랜덤하면 두 값이 우연히 같을 확률이 1/32. 1000번 돌려도 대부분 "매치 없음"이라 아무것도 검증하지 못한다. 범위를 좁히면(`% 4`) 흥미로운 케이스가 훨씬 자주 나온다.

또한 **존재할 수 없는 조합**을 만들면 가짜 FAIL이 쏟아진다. 예: "정수 명령어인데 FP 오퍼랜드를 읽음". 실제 하드웨어에 없는 입력이므로 **명령어 종류별로 묶어서 제약**해야 한다:

```verilog
case({$random} % 4)
    0: begin /* 정수    */ uses_FRs1=0; uses_FRs2=0; ... end
    1: begin /* FP산술  */ uses_FRs1=1; uses_FRs2=1; ... end
    2: begin /* FLW     */ uses_Rs1=1;  uses_FRs1=0; ... end
    3: begin /* FSW     */ uses_Rs1=1;  uses_FRs2=1; ... end
endcase
```

### `$random` 함정
- `$random`은 **부호있는 32비트**. `$random % 8`은 **-7~7**이 나온다
- unsigned로: `$random & 5'h7` 또는 `{$random} % 8`
- `% N` 은 **0 ~ (N-1)**. "N까지"가 아니다
- seed를 고정하면 FAIL 시 같은 시퀀스를 재현할 수 있다

### 참조 모델은 DUT와 "다른 방식"으로 쓴다

같은 방식으로 쓰면 **버그까지 복사**된다. 추상화 수준을 바꾼다.

예: DUT는 조건에서 곧바로 인코딩된 코드를 뱉지만, 모델은
1. 먼저 "각 오퍼랜드의 출처"를 심볼로 결정 (`NONE` / `FROM_MEM` / `FROM_WB`)
2. 그 다음 출처 → 코드로 인코딩

접근이 다르므로 인코딩 오타·우선순위 실수·케이스 누락이 잡힌다.

**한계**: 작은 조합회로는 "로직이 곧 사양"이라 완전히 독립적인 모델을 만들기 어렵다.
- ✅ 잡히는 것 — 인코딩 오타, 우선순위 실수, 케이스 누락, 신호 잘못 대입
- ❌ 못 잡는 것 — 사양 자체를 잘못 이해한 경우 (모델도 같이 틀림)

후자는 **directed 테스트로 "이 시나리오는 이래야 한다"를 명시**해야 잡힌다.

## 9. 커버리지 — "몇 번 돌렸다"는 의미 없다

랜덤 1000회가 통과했다고 검증이 끝난 게 아니다. **실제로 어떤 시나리오를 밟았는지 측정**해야 한다.

실측 예 (Project10 포워딩 유닛, 주소 범위 `% 4`):

| 결과 분포 | 횟수 |
|---|---|
| 포워딩 없음 | 801 |
| MEM만 | 95 |
| WB만 | 99 |
| **이중 포워딩** | **5** |
| **both 코드** | **7** |

→ **80%는 아무것도 검증하지 않았고**, 가장 까다로운 이중 포워딩은 5번뿐.
버그가 그 경로에 있었다면 운에 맡긴 셈이다.

**개선 방법**
1. 랜덤 범위를 좁혀 흥미로운 케이스 확률을 올린다 (`% 8` → `% 4` 로 발생 2배)
2. "아무것도 안 함" 케이스의 가중치를 낮춘다
3. **희귀 케이스는 directed로 못 박는다** ← 근본 해결

## 10. directed와 random은 보완재

| | 역할 |
|---|---|
| **directed** | "내가 **의도한** 시나리오가 되나" — 경계·특수·희귀 케이스를 **확실히** |
| **random** | "내가 **생각 못한** 조합이 깨지나" — 넓게 |

둘 다 쓴다. 실무도 그렇다.

## 11. 흔한 함정 정리

| 함정 | 증상 |
|---|---|
| 초기화 안 함 | 이전 케이스 값이 남아 오염 → `clr` task 필수 |
| `#1` 없이 바로 확인 | 옛 출력값을 봄 |
| DUT 포트 빠뜨림 | floating(`z`) → 전부 FAIL |
| 출력 wire 폭 누락 | 값이 잘려 절대 매치 안 됨 (Verilog는 폭 안 쓰면 **1비트**) |
| 카운터를 `reg`로 1비트 선언 | `x` 또는 뒤집힘 → **`integer`** 사용 + 0 초기화 |
| 기대값을 DUT에서 베낌 | 항상 PASS, 검증 효과 0 |
| `$finish` 없음 | 종료 안 됨 |
| 최종 요약 없음 | PASS/FAIL을 눈으로 세야 함 |
| 랜덤에 제약 없음 | 불가능한 조합이 가짜 FAIL 생성 |

## 12. 앞으로 (SystemVerilog / UVM)

지금 하는 것이 1단계. 순서는:

1. **directed self-checking** ← 현재
2. **constrained random + 참조 모델** ← 현재 (Project10)
3. **커버리지 주도 검증** (functional / code coverage)
4. **SVA** (assertion으로 불변식 표현)
5. **UVM** (agent / driver / monitor / scoreboard로 위 전부를 표준 구조화)

지금 손으로 하는 일이 UVM이 자동화해주는 일의 축소판이다.
직접 해봤기 때문에 UVM의 각 구성요소가 왜 필요한지 이해할 수 있다.
