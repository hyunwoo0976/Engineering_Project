# Project 5 — 배경지식

주제: **ALU 구조, 연산 선택과 MUX, 조합 always의 완전성과 래치, 상태 플래그**

---

## 1. ALU란

**Arithmetic Logic Unit** — 산술 연산과 논리 연산을 수행하는 조합 회로.
CPU 실행(EX) 단계의 핵심이다.

| 구성 | 내용 |
|---|---|
| 입력 | 오퍼랜드 A, B + 연산 선택 신호 |
| 출력 | 결과 + 상태 플래그 |
| 성질 | **조합 회로** — 클럭 없이 즉시 결과가 나온다 |

전형적인 연산 집합:

| 분류 | 연산 |
|---|---|
| 산술 | ADD, SUB, (INC, DEC) |
| 논리 | AND, OR, XOR, NOT |
| 시프트 | SLL, SRL, SRA |
| 비교 | SLT (Set Less Than) |

이 프로젝트는 ADD / SUB / AND / OR 4개. Project 10에서는 시프트와 비교까지 확장되어
`calculate_group`, `logical_group`, `shift_group`으로 분리된다.

## 2. 연산 선택은 MUX다

ALU에서 흔한 오해가 "선택된 연산만 실행된다"는 것이다. 하드웨어는 그렇지 않다.

```
     ┌──────────┐
A,B ─┤ 가산기    ├─┐
     └──────────┘ │
     ┌──────────┐ │
A,B ─┤ 감산기    ├─┤
     └──────────┘ ├── MUX ── result
     ┌──────────┐ │     ▲
A,B ─┤ AND      ├─┤     │
     └──────────┘ │   mode
     ┌──────────┐ │
A,B ─┤ OR       ├─┘
     └──────────┘
```

**모든 연산기가 게이트로 존재하고 항상 계산한다.** MUX가 그중 하나를 고를 뿐이다.

| 관점 | 의미 |
|---|---|
| 면적 | 4개 연산기가 모두 실체로 존재 |
| 전력 | 쓰지 않는 연산기도 스위칭하며 전력을 소비 |
| 지연 | 가장 느린 연산기(보통 가산기)가 임계 경로 |

Verilog의 `case`, `if`, `? :` 는 조합 문맥에서 전부 **MUX로 합성**된다.

### 전력을 아끼려면

**오퍼랜드 아이솔레이션(operand isolation)** — 쓰지 않는 연산기의 입력을 고정해
내부 스위칭을 막는 기법이 있다. 합성 도구가 자동으로 넣어주기도 한다.

Project 10에서 FPU를 `FPU_en`으로 게이팅하는 것이 같은 발상이다.

### 지연 최적화

가산기가 가장 느리므로, 실무 ALU는 산술 경로와 논리 경로를 분리해
논리 연산 결과가 먼저 확정되게 만들기도 한다.

## 3. ★ 조합 always의 완전성 — 래치가 생기는 이유

이 프로젝트에서 실제로 발생한 문제([error_log R01](error_log.md))의 배경.

### 규칙

> **조합 `always` 블록의 모든 실행 경로에서, 모든 출력에 값을 대입해야 한다.**

대입하지 않는 경로가 있으면 그 신호는 **이전 값을 유지**해야 하므로,
합성 도구가 **래치(level-sensitive latch)** 를 만든다.

```verilog
always @(*) begin
    case (mode)
        2'b00: begin result = ...; cout = add_cout; end
        2'b01: begin result = ...; cout = sub_cout; end
        2'b10: result = ...;        // cout 미대입 → 래치
        2'b11: result = ...;        // cout 미대입 → 래치
    endcase
end
```

### 래치가 왜 문제인가

| 문제 | 내용 |
|---|---|
| **의도하지 않은 기억** | 조합 회로여야 하는데 상태를 갖는다 |
| **타이밍 분석 곤란** | 래치는 레벨 감지 소자라 STA가 복잡해진다 |
| **레이스 위험** | 클럭이 아닌 신호로 열리고 닫혀 예측이 어렵다 |
| **시뮬 ≠ 합성** | 시뮬에서는 "그냥 값이 유지"되지만 실제 회로는 래치가 된다 |

### 해결 — 세 가지 방법

```verilog
// ① 맨 위에 기본값 (권장)
always @(*) begin
    result = 0;
    cout   = 0;
    case (mode) ... endcase
end

// ② 모든 분기에서 모든 신호 대입
2'b10: begin result = a & b; cout = 1'b0; end

// ③ default 추가 (case 값이 빠지는 것만 막음. 신호 누락은 못 막는다)
default: begin result = 0; cout = 0; end
```

**①이 가장 안전하다.** 신호를 나중에 추가해도 기본값이 자동으로 적용된다.

### SystemVerilog의 `always_comb`

```systemverilog
always_comb begin ... end
```

`always_comb`를 쓰면 **도구가 래치 추론을 오류로 잡아준다.**
`always @(*)`는 조용히 래치를 만들지만, `always_comb`는 경고한다.
Project 10 이후 SystemVerilog로 넘어가면 이 실수가 구조적으로 방지된다.

## 4. 상태 플래그 (Status Flags)

ALU는 결과만 내는 게 아니라 **결과의 성질**을 플래그로 보고한다.

| 플래그 | 이름 | 조건 |
|---|---|---|
| **Z** | Zero | 결과가 0 |
| **N** | Negative | 결과의 MSB가 1 (부호 있는 해석) |
| **C** | Carry | 무부호 자리올림/빌림 |
| **V** | Overflow | 부호 있는 범위 초과 (`c_N ^ c_{N-1}`) |

### 플래그의 용도 — 분기

```
cmp  x1, x2      → 내부적으로 x1 - x2 를 계산해 플래그만 갱신
beq  label       → Z 플래그가 1이면 분기
blt  label       → N ^ V 로 판정
```

x86, ARM은 이 방식(플래그 레지스터)을 쓴다.

**RISC-V는 플래그 레지스터가 없다.** 대신 분기 명령어가 두 레지스터를 직접 비교한다.
```
beq x1, x2, label     ← 비교와 분기를 한 명령어로
slt x3, x1, x2        ← 비교 결과를 정수 레지스터에 0/1로 저장
```
파이프라인에서 플래그는 전역 상태라 해저드 관리가 복잡해지기 때문이다.

Project 10의 ALU가 `ZF`(Zero Flag)와 `sign`을 출력하고, `PCSrc`가 그것으로
분기를 판정하는 구조가 이 절충이다.

### 이 프로젝트는 `cout`만 있다

Z, N, V가 없다. 확장한다면:
```verilog
assign ZF = (result[N-1:0] == 0);
assign NF = result[N-1];
assign VF = c_N ^ c_{N-1};      // 가산기 내부 캐리 필요
```

## 5. 결과 비트폭 설계 — 5비트 vs 4비트+캐리

4비트 + 4비트 덧셈의 결과는 최대 5비트(`1111 + 1111 = 11110`)다. 두 가지 선택이 있다.

| 방식 | 장점 | 단점 |
|---|---|---|
| **5비트 `result`** (`result[4]` = 캐리) | 신호 하나. 값이 잘리지 않음 | 다음 모듈이 5비트를 받아야 함. 논리 연산에서 최상위 비트가 낭비 |
| **4비트 `result` + 1비트 `cout`** | 데이터 폭이 일정. 플래그로 분리되어 다루기 쉬움 | 신호가 둘 |

**실무는 후자를 쓴다.** 데이터패스 폭을 일정하게 유지하는 것이 중요하기 때문이다.
32비트 CPU에서 ALU 결과가 33비트가 되면 레지스터·버스·파이프라인 레지스터가 전부 33비트가 되어야 한다.
캐리는 **데이터가 아니라 상태 정보**이므로 플래그로 분리하는 것이 자연스럽다.

현재 코드는 5비트 `result`와 별도 `cout`을 **둘 다** 갖고 있어 mode 00에서 중복이다.

## 7. 랜덤 자극 (Random Stimulus)

이 프로젝트에서 `$random`을 처음 썼다.

### 왜 랜덤으로 바꿨나

규칙적인 입력(`b = 15 - a`)이 논리 연산 결과를 상수로 굳혀버렸다
(`a & ~a = 0`, `a | ~a = 1111`). → [error_log E02](error_log.md)

**사람이 만든 규칙적 패턴은 우연한 상관관계를 갖기 쉽다.** 랜덤은 그걸 깨뜨린다.

### `$random` 사용 시 주의

| 항목 | 내용 |
|---|---|
| 반환 | **32비트 부호있는 정수** |
| `$random % 8` | **-7 ~ 7** (음수 포함). 의도와 다르다 |
| unsigned로 | `$random & 5'h7` 또는 `{$random} % 8` |
| 좁은 reg에 대입 | `reg [3:0] x = $random;` → 하위 4비트만 (0~15). 이 프로젝트는 이 방식 |
| 재현성 | seed를 고정해야 FAIL 시 같은 시퀀스 재현 가능 |

### 랜덤만으로는 부족하다

랜덤은 "생각 못한 조합"을 훑지만 **경계 케이스를 보장하지 않는다.**
- `a = 0`, `b = 0`
- `a = 15`, `b = 15` (최대)
- `a = b` (감산 결과 0)
- 캐리 전 구간 전파 (`1111 + 0001`)

이런 것은 directed 케이스로 명시해야 한다.
Project 10에서 랜덤 1000회를 돌렸을 때 흥미로운 케이스가 몇 번밖에 안 나온 것이
같은 이야기다.

## 8. ALU가 CPU에서 하는 일

```
IF ──► ID ──► EX ──► MEM ──► WB
              │
              └── ALU
```

| 명령어 종류 | ALU가 하는 계산 |
|---|---|
| R-type (`add`, `and`) | 연산 자체 |
| I-type (`addi`) | 레지스터 + 즉시값 |
| **LW / SW** | **주소 계산** (`rs1 + offset`) |
| **Branch** | 비교 (내부적으로 감산) |
| **JALR** | 타겟 주소 (`rs1 + imm`) |

ALU는 산술 명령어만 쓰는 게 아니라 **주소 계산과 분기 판정에도 동원**된다.
그래서 ALU가 임계 경로에 놓이기 쉽고, 포워딩 MUX가 그 앞에 붙으면 지연이 더 늘어난다.

Project 10에서 `ALU_Control`이 `funct3`/`funct7`/`ALUOp`를 조합해 어떤 연산을 할지 정하고,
`ALU_port_MUX`가 오퍼랜드를 고르는 구조가 여기서 출발한다.

## 9. 용어 정리

| 용어 | 뜻 |
|---|---|
| **ALU** | Arithmetic Logic Unit. 산술·논리 연산 조합 회로 |
| **연산 선택 = MUX** | `case`/`if`가 합성되면 MUX가 된다 |
| **래치 추론** | 조합 always에서 대입 누락 시 생기는 의도치 않은 기억 소자 |
| **`always_comb`** | SystemVerilog. 래치 추론을 오류로 잡아준다 |
| **상태 플래그 (Z/N/C/V)** | Zero / Negative / Carry / Overflow |
| **오퍼랜드 아이솔레이션** | 미사용 연산기의 입력을 고정해 전력 절감 |
| **directed / random** | 지정 케이스 / 무작위 자극 |
