## E01 · 시프트 레지스터가 옆으로 이동하지 않음

- **[파형]** `img_shift_register/1.옆으로 이동이 안되는 상태.PNG`

- **[증상]** 4비트로 만들던 초기 버전.
  ```
  D_a[3:0] = 5        (입력값 로드 시도)
  Q_a[3:0] = 0        ← 계속 0. load도 shift도 반영되지 않음
  N        = x → 0
  ```
  `load` 펄스가 8~12ns에 있고 그 사이 클럭 상승이 있는데도 `Q_a`가 0에서 움직이지 않는다.

- **[원인]** 기록해두지 않았다. 현재 코드는 32비트로 재작성되어 있어 당시 상태를 복원할 수 없다.

  파형에서 읽을 수 있는 것: `load`가 assert된 클럭 에지에서 `Q_a <= D_a`가 일어나지 않았다.
  `Q_a`가 `x`가 아니라 `0`이라는 점에서 리셋은 동작했고, **`load` 경로만 반영되지 않은** 상태다.

- **[확인]** 32비트 버전에서 정상 동작.
  `img_shift_register/올바른파형2.PNG`, 그리고 시뮬레이션에서 `D_in = D_out = a5a5f0f0` 일치.

- **[메모]** 4비트 → 32비트로 옮기는 과정에서 해결되었다. 다시 만들면서 자연히 고쳐진 셈이라
  원인이 무엇이었는지 남지 않았다. **작게 재현해서 원인을 특정한 뒤 고치는 편이 낫다.**

## E02 · 랜덤 입력값이 검증에 부적합

- **[파형]** `img_shift_register/올바른 파형 하지만 랜덤값이 4가나와 아쉬운상태.PNG`

- **[증상]** 동작 자체는 정상인데 **확인이 어렵다.**
  ```
  D_in  = 00000004
  D_out = 800.. → 400.. → 200.. → ... → 000.. → 00000004
  N     : 펄스가 딱 한 번
  ```

- **[원인]** `4 = 0000...0100` 은 **'1' 비트가 하나뿐**이다.
  직렬 스트림이 거의 전부 0이라 `N` 선에 펄스가 한 번만 나타난다.

  이러면 파형으로 다음을 구분할 수 없다.
  - 비트가 제대로 하나씩 이동하는지
  - 순서가 뒤집히지 않았는지
  - 중간에 비트가 누락되지 않았는지

  결과값이 맞더라도 **우연히 맞은 것인지 알 수 없다.**

- **[수정]** 입력을 **`32'hA5A5_F0F0`** 으로 교체.
  ```
  A5A5F0F0 = 1010 0101 1010 0101 1111 0000 1111 0000
  ```
  `1010` 반복과 `1111 0000` 블록이 섞여 있어, 직렬 스트림에 전이가 많다.
  파형에서 비트 이동을 눈으로 따라갈 수 있고, 순서가 뒤집히면 즉시 보인다.

- **[확인]** 시뮬레이션 결과 `D_in = D_out = a5a5f0f0`.
  `D_out`이 `800..→400..→200..` 순으로 우측 시프트되며 채워지는 것도 파형에서 확인.

- **[메모]** 랜덤이 항상 좋은 자극은 아니다. **관측성(observability)** 이 필요한 경우에는
  전이가 많은 패턴을 직접 고르는 편이 낫다.
  `A5`, `5A`, `F0`, `0F`, `AA`, `55` 같은 값이 이런 목적으로 흔히 쓰인다.

## 재검토에서 확인한 사항

### R01 · 테스트벤치가 클럭 에지에서 제어 신호를 바꾼다

```verilog
wait(fin==1'b1);
@(posedge clk);
shift=0;            // ← 클럭 에지와 같은 시각
```

`shift=0`이 클럭 상승과 **같은 시간 단위**에서 실행된다.
같은 시각에 RX/TX의 `always @(posedge clk)`도 실행되므로,
**어느 쪽이 먼저인지 Verilog가 보장하지 않는다** (레이스).

현재 iverilog에서는 결과가 맞게 나온다. 다만 시뮬레이터나 버전이 바뀌면
32번째 시프트 이후 한 번 더 시프트되어 `D_out`이 밀릴 수 있다.

- **[조치안]** 제어 신호는 클럭 에지에서 떨어진 시점에 바꾼다.
  ```verilog
  @(negedge clk); shift=0;        // 또는
  @(posedge clk); #1; shift=0;
  ```

### R02 · `src_latch/`에 사용되지 않는 파일들

| 파일 | 상태 |
|---|---|
| `SR_latch.v` | `.f`에 없음. 학습용으로 만든 것 |
| `D_latch.v` | `.f`에 없음 |
| `D_flip_flop.v` | `.f`에 없음 |
| `RX_shift_reg.v`, `TX_shift_reg.v`, `Top_register.v` | 실제 사용 |

래치 → 플립플롭 → 시프트 레지스터로 올라가는 과정을 만들어본 파일들이 남아 있다.
버리지 않은 것은 좋지만, 어느 것이 최종 설계인지 구분되지 않는다.
`study/` 같은 하위 폴더로 분리하거나 README에 명시하면 정리된다.

### R03 · `.f` 파일의 경로 기준이 프로젝트마다 다르다

| 프로젝트 | `.f` 경로 형태 | 실행 위치 |
|---|---|---|
| Project 2~5 | `./src_...`, `../ProjectN/...` | 각 프로젝트 폴더 |
| Project 6 | `./ProjectN/...` | `verilog/` |
| **Project 7** | `./verilog/ProjectN/...` | **저장소 루트** |

같은 명령을 어디서 실행해야 하는지 매번 달라진다. 하나로 통일하는 편이 낫다.

### R04 · 자동 판정이 없음

`$display`도 `$monitor`도 없어 콘솔 출력이 전혀 없다. 파형을 열어야 결과를 알 수 있다.
직렬 전송은 기대값이 명확하므로 한 줄로 판정할 수 있다.

```verilog
wait(fin==1'b1);
@(negedge clk);
if (D_out !== D_in) $display("[FAIL] D_in=%h D_out=%h", D_in, D_out);
else                $display("[PASS] %h", D_out);
```

## 교훈

1. **원인을 특정하기 전에 다시 만들면 기록이 남지 않는다.** E01은 32비트로 재작성하면서
   해결됐지만 무엇이 문제였는지 모른다. 작게 재현해 원인을 확인한 뒤 고치는 편이 낫다
2. **랜덤이 항상 좋은 자극은 아니다.** `4`처럼 전이가 거의 없는 값은 동작을 확인할 수 없다.
   관측성이 필요하면 `A5A5F0F0` 같은 패턴을 직접 고른다 (E02)
3. **제어 신호는 클럭 에지에서 떨어진 시점에 바꾼다.** 같은 시각에 바꾸면 레이스다 (R01)
4. **결과가 맞아도 "왜 맞는지" 확인할 수 있어야 한다.** 값 하나가 우연히 맞는 것과
   비트가 순서대로 이동하는 것을 구분할 수 있는 자극을 써야 한다
