# Project 8 — 오류 기록

[← Project 8 README](../README.md) · [Design notes](정리.md) · [Background](배경지식.md)

레지스터 파일 → ALU → 입력 MUX → 레지스터 파일로 돌아오는 피드백 경로를 처음 묶으면서 확인한 오류 기록.
기록 형식은 **파형 / 증상 / 원인 / 수정 / 확인 / 교훈** 순서다.

> 당시 RTL의 중간 버전은 남아 있지 않다. 사진과 현재 코드가 함께 증명하는 내용은 확정해서 적고,
> 사진만으로 한 줄의 원본 코드를 특정할 수 없는 부분은 **역추정**이라고 표시했다.

## E01 · 첫 레지스터 값이 기대한 주소에 저장되지 않음 — 클럭 에지와 TB 대입이 겹침

- **[파형]** [`top_system 오류.PNG`](../img_top%20system/top_system%20오류.PNG)

  ![초기 top system 오류 파형](../img_top%20system/top_system%20오류.PNG)

- **[증상]** 테스트벤치 입력 `TB_v`는 `4 → 1`로 바뀌었지만, ALU 입력인 `dout1_a`는 계속 0이고
  `dout2_b`에만 4가 나타났다. 따라서 `mode=00`에서 기대한 두 레지스터의 합 대신 한쪽 값만 반영된
  `alu_v=04`가 나왔다. 피드백 값 `MUX_reg`도 `04 → 00 → 04`처럼 기대와 다르게 반복됐다.

- **[원인]** 현재 테스트벤치에도 첫 write 제어를 `@(posedge clk)` 직후 같은 시뮬레이션 시간에
  바꾸는 코드가 남아 있다 (`tb/Top_system_tb.v:36~39`). DUT의 `always @(posedge clk)`와 TB의
  blocking 대입이 같은 active region에서 경쟁하므로, DUT가 새 `we/w_add/TB_v`를 볼지 이전 값을 볼지
  실행 순서에 의존한다. 사진의 값 이동은 이 **testbench race**와 일치한다.

  두 번째 write에는 `#1`이 들어가 있지만(`:41~45`), 첫 write에는 없어서 자극 방식도 일관되지 않다.

- **[수정]** write 주소·데이터·`we`를 상승 에지보다 먼저 안정시키고, 다음 상승 에지에서 DUT가
  샘플하도록 순서를 분리했다. 파형을 읽을 때도 “값을 바꾼 시각”과 “레지스터가 저장한 에지”를
  구분했다.

- **[확인]** [`최종파형.PNG`](../img_top%20system/최종파형.PNG)에서 `mem[0]=04`, `mem[1]=01`이
  각각 유지되고, 읽기 주소를 고정한 뒤 ALU 결과가 mode별로 `05`, `03`, `00`, `05`로 나온다.

  ![Project 8 최종 파형](../img_top%20system/최종파형.PNG)

- **[교훈]** 순차회로 테스트벤치에서는 클럭 에지에 맞춰 입력을 바꾸면 안 된다. 에지는 DUT가
  값을 **받는 순간**이고, TB는 그 전에 값을 준비해야 한다. `negedge`에서 자극하거나 `posedge` 뒤
  작은 지연을 둔 뒤 다음 `posedge`에서 저장시키면 경쟁을 피할 수 있다.

## E02 · `dout2`가 4로 찍힘 — 두 읽기 포트가 같은 주소를 보고 있었음

- **[파형]** [`dout2가 4가 찍히는오류.PNG`](../img_top%20system/dout2가%204가%20찍히는오류.PNG)

  ![dout2가 4로 보인 파형](../img_top%20system/dout2가%204가%20찍히는오류.PNG)

- **[증상]** 내부 메모리는 `mem[0]=04`, `mem[1]=01`로 올바르게 저장됐는데, 초반에
  `dout1=4`, `dout2=4`가 동시에 나타났다. 두 번째 포트는 1을 읽어야 한다고 생각해 오류로 봤다.

- **[원인]** 파형에서 `dout2`가 4인 구간은 두 번째 읽기 주소가 아직 0을 가리키는 구간이다.
  `r_add2`가 1로 바뀌자 `dout2`도 바로 1로 바뀐다. 현재 RTL은
  `dout2 = mem[r_add2][N-1:0]`인 조합 읽기 구조(`dual_port_reg.v:20`)이므로, 주소 0이면
  `mem[0]=4`가 나오는 것이 정상이다.

- **[수정]** 두 피연산자를 읽기 전에 `r_add1=0`, `r_add2=1`을 명시하고 주소가 안정된 뒤 ALU 결과를
  관찰했다. 즉 데이터 저장 문제가 아니라 **읽기 주소와 관찰 시점** 문제로 분리했다.

- **[확인]** 같은 파형 후반과 최종 파형에서 `r_add2=1`인 동안 `dout2/mem[1]=1`이 일치한다.
  결과적으로 이 항목은 RTL 고장이 아니라 파형을 너무 이른 구간에서 읽은 해석 오류였다.

- **[교훈]** 레지스터 파일 출력이 이상하면 데이터부터 의심하지 말고
  **주소 → 해당 메모리 원소 → 출력**을 한 화면에 놓고 비교한다. 두 read port는 독립이지만,
  같은 주소를 주면 당연히 같은 값을 낸다.

## 재검토에서 확인한 사항

### R01 · 파라미터 `N`의 폭 의미가 신호마다 다름

- `TB_v`, `dout1`, `dout2`는 `[N-1:0]`이지만 `MUX_reg`, `alu_v`, `mem[]`은 `[N:0]`이다.
- `N=4`일 때 전자는 4비트, 후자는 5비트다. ALU carry까지 피드백하려는 구조지만 레지스터 출력에서는
  다시 하위 4비트만 잘라낸다 (`dual_port_reg.v:19~20`).
- 현재 동작은 의도와 맞을 수 있으나, `N` 하나가 두 폭을 뜻해 유지보수할 때 혼동하기 쉽다.
  데이터 폭과 carry 포함 폭을 이름으로 분리하는 편이 명확하다.

### R02 · 네 개 레지스터 중 두 개만 검증함

- 메모리는 `mem[0:3]` 네 칸인데 테스트는 주소 0과 1만 쓴다.
- 주소 2·3, 같은 주소 동시 읽기, write와 read가 같은 주소일 때의 동작은 확인하지 않았다.
- 최종 파형은 현재 시나리오의 성공 증거이지 레지스터 파일 전체 상태공간의 증명은 아니다.

### R03 · 자동 판정이 없음

- 최종 파형으로 `05/03/00/05`를 눈으로 확인했지만 테스트벤치가 기대값과 비교하지 않는다.
- mode별 참조식을 두고 mismatch 시 `$error`를 내면 이후 수정에서 생기는 회귀를 자동으로 잡을 수 있다.

## 최종 확인

| 확인 항목 | 파형 결과 |
|---|---|
| register 0 / 1 저장 | `04` / `01` |
| mode `00` | `4 + 1 = 5` |
| mode `01` | `4 - 1 = 3` |
| mode `10` | `4 & 1 = 0` |
| mode `11` | `4 \| 1 = 5` |

블록 연결 의도는 [`탑모듈 블록 다이어그램.jpg`](../img_top%20system/탑모듈%20블록%20다이어그램.jpg)에 남아 있다.

## 교훈

1. 순차회로 TB는 데이터를 클럭 에지 **전에** 준비한다.
2. 출력이 이상할 때는 값만 보지 말고 그 값을 고르는 주소와 MUX select를 같이 본다.
3. 정상 파형 한 장과 “전체 검증 완료”는 다르다. 주소·연산별 자동 판정이 필요하다.
