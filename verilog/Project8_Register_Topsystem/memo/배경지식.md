## 1. 단일 레지스터에서 레지스터 파일로

Project 6·7까지의 레지스터는 주로 값 하나 또는 직렬 데이터 한 줄을 저장했다. CPU처럼 여러 값을
동시에 다루려면 작은 저장소 안에서 **어느 칸에 쓸지**, **어느 두 칸을 읽을지** 선택해야 한다.
이 구조가 register file이다.

```text
                   write address
                        │
data in ───────────────▶│  register file
                        │  mem[0] mem[1] mem[2] mem[3]
read address 1 ─────────┤────────▶ operand A
read address 2 ─────────┤────────▶ operand B
```

이 프로젝트의 배열은 `reg [N:0] mem[0:3]`이다.

- `[N:0]` — 각 원소의 비트폭(packed dimension)
- `[0:3]` — 원소 네 개의 인덱스(unpacked dimension)

즉 “5비트짜리 서랍 네 칸”이다. 주소 2비트가 네 칸 중 하나를 고른다.

## 2. 왜 read port가 두 개인가

ALU의 대부분 연산은 두 operand가 필요하다.

```text
ADD: A + B
SUB: A - B
AND: A & B
OR : A | B
```

한 사이클에 A와 B를 동시에 공급하려면 read port도 두 개여야 한다. read port가 하나뿐이면 한 값을
읽고 다음 사이클에 다른 값을 읽어야 하므로 추가 저장소와 제어 사이클이 필요하다.

```verilog
assign dout1 = mem[r_add1][N-1:0];
assign dout2 = mem[r_add2][N-1:0];
```

두 포트는 같은 메모리를 보지만 주소 선택은 독립이다. 따라서 `r_add1==r_add2`라면 두 출력이 같은
값인 것이 정상이다. 실제로 이를 오류로 오해했던 과정은 [error log E02](error_log.md)에 기록했다.

## 3. 동기 쓰기와 비동기 읽기

### 동기 쓰기

```verilog
always @(posedge clk or posedge reset) begin
    if (reset)
        ...
    else if (we)
        mem[w_add] <= din;
end
```

`we=1`인 상승 에지에서만 값이 저장된다. 주소와 데이터는 에지 **전에** 안정돼 있어야 한다.
에지와 같은 시각에 테스트벤치가 값을 바꾸면 DUT와 TB의 실행 순서가 경쟁하는 race가 생긴다.

### 비동기 읽기

`assign dout = mem[address]`는 클럭을 기다리지 않는다. 주소가 바뀌면 조합 경로를 지나 출력도 바뀐다.

| 동작 | 클럭 필요 | 의미 |
|---|---|---|
| write | 필요 | 상승 에지에서 상태 변경 |
| read | 불필요 | 현재 주소의 값을 즉시 선택 |

이 조합은 CPU register file에서 흔히 쓰인다. 한 사이클의 ID 단계에서 두 operand를 읽고, WB 단계가
상승 에지에 결과를 쓴다.

## 4. 데이터패스 피드백

Project 8의 핵심은 ALU 결과가 끝에서 사라지지 않고 다시 register file의 입력으로 돌아온다는 점이다.

```text
                 ┌────────────── feedback ──────────────┐
                 │                                      │
register file ──▶ operand A/B ──▶ ALU ──▶ result ──▶ MUX ──▶ din
                                                      ▲
external TB value ────────────────────────────────────┘
```

처음에는 테스트벤치 값으로 register를 채워야 하고, 그 다음부터는 ALU 결과를 다시 저장해야 한다.
그래서 MUX가 두 입력 중 하나를 고른다.

```verilog
assign din = count ? alu_v : {1'b0, TB_v};
```

- `count=0` — 외부 값 로드
- `count=1` — ALU 결과 피드백

MUX는 단순한 배선 선택기지만 “데이터가 어디서 오는가”를 결정하므로 데이터패스의 방향을 바꾼다.
Project 9에서는 이 선택을 사람이 직접 바꾸는 수준을 넘어 FSM이 계산 시점을 통제한다.

## 5. 데이터 경로와 제어 경로

| 구분 | 이 프로젝트의 신호 | 역할 |
|---|---|---|
| 데이터 | `TB_v`, `dout1`, `dout2`, `alu_v`, `MUX_reg` | 실제 계산 값 운반 |
| 주소 | `w_add`, `r_add1`, `r_add2` | register 선택 |
| 제어 | `we`, `count`, `mode`, `reset` | 저장·입력원·연산 결정 |
| 시간 기준 | `clk` | 상태가 바뀌는 순간 결정 |

데이터가 맞아도 제어 시점이 틀리면 잘못된 주소에 저장된다. 반대로 주소와 제어가 맞아도 ALU 입력이
준비되기 전에 관찰하면 이전 값이 보인다. 하드웨어 디버깅에서는 값만 보지 않고 이 네 종류를 함께
시간축에 놓아야 한다.

## 6. 비트폭과 carry

ALU 입력은 N비트지만 덧셈 결과는 carry까지 포함해 N+1비트가 될 수 있다.

```text
4'b1111 + 4'b0001 = 5'b1_0000
```

현재 설계는 `alu_v`, `MUX_reg`, `mem[]`을 `[N:0]`으로 두어 carry까지 저장할 수 있지만,
register read 출력은 `[N-1:0]`만 꺼낸다. 다음 계산에는 하위 N비트만 재사용되는 셈이다.

이 선택은 틀렸다기보다 **인터페이스 규칙을 명확히 해야 하는 지점**이다.

- carry도 다음 연산의 데이터인가?
- 아니면 별도 flag인가?
- register file의 데이터 폭은 N인가 N+1인가?

Project 9에서는 carry와 negative를 데이터에서 분리된 flag로 다루며 이 질문을 더 명확하게 만든다.

## 7. 파형을 읽는 순서

register system이 틀렸을 때 다음 순서로 보면 원인을 빨리 좁힐 수 있다.

1. reset 뒤 `mem[]`이 0인가
2. 상승 에지 전에 `we/w_add/din`이 안정됐는가
3. 상승 에지 뒤 선택한 `mem[w_add]`만 바뀌었는가
4. `r_add1/r_add2`와 `dout1/dout2`가 대응하는가
5. `mode`와 ALU 결과가 맞는가
6. `count`가 고른 MUX 입력이 `din`으로 돌아오는가

이것은 데이터가 흐르는 컨베이어벨트를 역방향으로 추적하는 것과 같다. 출력이 잘못됐다고 ALU부터
뜯는 것이 아니라, 출력까지 오는 각 선택 지점을 하나씩 확인한다.

## 8. 용어 정리

| 용어 | 뜻 |
|---|---|
| **Register file** | 여러 레지스터를 주소로 선택해 읽고 쓰는 저장 블록 |
| **Read port / Write port** | 값을 읽는 통로 / 값을 기록하는 통로 |
| **Synchronous write** | 클럭 에지에서만 저장값이 바뀌는 쓰기 방식 |
| **Asynchronous read** | 주소가 바뀌면 클럭 없이 출력이 바뀌는 읽기 방식 |
| **Datapath** | 실제 데이터가 저장·선택·계산되며 흐르는 경로 |
| **Control path** | 주소, enable, mode처럼 데이터 흐름을 지시하는 경로 |
| **Write-back** | 연산 결과를 다시 레지스터에 기록하는 과정 |
| **Feedback** | 블록의 출력을 다시 앞쪽 입력으로 되돌리는 연결 |
| **MUX** | 여러 입력 가운데 제어 신호가 고른 하나를 출력하는 회로 |

## 9. 인접 개념 / 다음 단계

| Project 8 개념 | 다음 사용처 |
|---|---|
| 두 read port | CPU의 `Rs1`, `Rs2` 동시 읽기 |
| 한 write port | CPU WB 단계의 `Rd` 기록 |
| ALU 결과 피드백 | fetch/decode/execute 결과의 write-back |
| MUX 선택 | ALUSrc, MemToReg, forwarding MUX |
| 동기 write·비동기 read | CPU register file |
| 제어와 데이터 분리 | Project 9 FSM, Project 10 decoder/hazard unit |

Project 9에서는 수동 제어 신호 일부를 FSM이 만들고, Project 10에서는 instruction decoder와 hazard unit이
더 많은 MUX와 write enable을 제어한다.
