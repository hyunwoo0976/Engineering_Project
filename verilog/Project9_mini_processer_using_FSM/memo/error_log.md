# Project 9 — 오류 기록

[← Project 9 README](../README.md) · [Design notes](정리.md) · [Background](배경지식.md)

레지스터 파일과 ALU에 FSM 제어를 붙이면서 발생한 오류를 파형 순서대로 복원한 기록.
기록 형식은 **파형 / 증상 / 원인 / 수정 / 확인 / 교훈** 순서다.

> 당시 중간 RTL은 남아 있지 않다. 파일명·파형·현재 코드가 함께 뒷받침하는 부분은 확정해서 적고,
> 수정 전 한 줄을 재현할 수 없는 부분은 **현재 코드에서 역추정**이라고 표시했다.

---

## E01 · 첫 파형에서 ALU 결과와 플래그가 `x`

- **[파형]** [`파형 1차본.PNG`](../img_m_processer1/파형%201차본.PNG)

  ![Project 9 첫 파형](../img_m_processer1/파형%201차본.PNG)

- **[증상]** reset 해제 뒤 `din`과 주소, mode는 변하지만 `V/Z/P/C`가 오랫동안 `x` 또는
  붉은 미정 상태로 남았다. `start`를 올린 뒤에도 외부에서 어떤 계산이 유효한지 판단하기 어려웠다.

- **[원인]** 계산 경로의 입력이 준비되기 전부터 조합 ALU와 플래그 식이 그 값을 읽었다.
  레지스터 출력이 `x`이면 `result`와 `V/Z/C/N`도 연쇄적으로 `x`가 된다. 당시 carry 연결 문제(E03)도
  겹쳐 있었기 때문에 입력이 안정된 뒤에도 덧셈 관련 신호는 미정 상태가 남았다.

- **[수정]** reset → 두 레지스터 write → read address 지정 → `start` 순서로 단계를 나눴다.
  ALU 결과는 FSM의 `CALC` 상태에서만 유효하게 선택하도록 `S_calc`로 게이팅했다.

- **[확인]** 후속 결과 파형에서는 두 operand가 먼저 확정된 뒤 `start=1`, `mode=00~11` 순서로
  결과가 나타난다. 초기 `x` 구간과 유효 계산 구간을 구분할 수 있게 됐다.

- **[교훈]** `x`는 하나의 고장명이 아니라 **아직 값이 없는 상류 신호가 아래로 전파된 결과**다.
  가장 아래 출력부터 고치지 말고 operand와 제어 신호를 위에서 아래 순서로 추적한다.

## E02 · mode가 `01`이 되자 계산 결과가 0으로 꺼짐 — FSM이 ERROR 상태로 전이

- **[파형]** [`calc가 mode 01이되면 꺼지는현상.PNG`](../img_m_processer1/calc가%20mode%2001이되면%20꺼지는현상.PNG)

  ![mode 01에서 계산이 꺼진 파형](../img_m_processer1/calc가%20mode%2001이되면%20꺼지는현상.PNG)

- **[증상]** 입력이 `a=3`, `b=6`일 때 `mode=00` 덧셈 결과가 `9`까지 나온 뒤,
  `mode=01`로 바뀌는 시점부터 `alu_result=0`이 됐다. 내부 `sub_result=D`와 `add_result=A/9`는
  살아 있는데 최종 ALU 출력만 꺼졌다.

- **[원인]** 4비트 signed에서 `3 + 6 = 9`는 표현 범위 `-8~7`을 넘는다.
  두 입력의 sign bit는 0인데 결과 `1001`의 sign bit는 1이므로 `V=1`이다.
  FSM은 CALC 상태에서 `V`를 보면 ERROR로 전이하고(`m_FSM.v:34~40`), ERROR에서는 `S_calc=0`이 된다.
  ALU는 `S_calc`가 0이면 기본값 `result=0`을 내므로(`m_ALU.v:26~45`) mode 01이 원인처럼 보였지만,
  실제 원인은 **직전 덧셈 overflow**였다.

- **[수정]** 정상 연산 순서를 검증할 때는 overflow가 없는 `a=4`, `b=1`을 사용하고,
  overflow 검증은 `a=3`, `b=5`처럼 별도 시나리오로 분리했다. 파형에 `V`와 FSM 상태 신호를 함께
  올려 “mode 변경”과 “ERROR 진입”을 구분했다.

- **[확인]** [`결과 a=4,b=1.PNG`](../img_m_processer1/결과%20a=4,b=1.PNG)에서는
  `5 → 3 → 0 → 5`가 mode 00~11에 맞게 모두 나온다. 반면
  [`결과 a=3,b=5.PNG`](../img_m_processer1/결과%20a=3,b=5.PNG)에서는 덧셈 `8`과 동시에
  `V=1`, 다음 상태에서 결과 0이 되어 ERROR 경로가 의도대로 드러난다.

- **[교훈]** 시간상 동시에 보이는 변화가 인과관계라는 보장은 없다. mode가 바뀌며 출력이 꺼졌다면
  mode MUX뿐 아니라 **직전 사이클이 FSM 상태를 바꿨는지** 확인해야 한다.

## E03 · 덧셈 결과와 carry가 계속 `x` — 올림수 체인이 상위 계층까지 연결되지 않음

- **[파형]** [`cin값이 이상하게 나오는것확인.PNG`](../img_m_processer1/cin값이%20이상하게%20나오는것확인.PNG),
  [`덧셈 unknown, 올림수가 전달안되는 상황.PNG`](../img_m_processer1/덧셈%20unknown,%20올림수가%20전달안되는%20상황.PNG)

  ![carry chain이 미정인 파형](../img_m_processer1/덧셈%20unknown,%20올림수가%20전달안되는%20상황.PNG)

- **[증상]** 감산 경로 `sub_re`는 `F/B/C`처럼 값이 나오지만 `add_re`, `add_result`, 최종 carry
  관련 신호는 계속 `x`였다. 내부 full-adder 단계의 `cin/cout`도 첫 미정값에서 뒤 비트로 연쇄 전파됐다.

- **[원인]** 사진 파일명과 현재 코드의 수정 흔적을 함께 보면, 수정 전에는 ripple-carry의 시작 `cin`
  또는 마지막 `cout`이 상위 ALU까지 완전히 연결되지 않았다. carry chain은 한 비트의 `cout`이 다음 비트
  `cin`이 되는 구조라 시작점 하나가 `x`면 모든 상위 sum/carry가 `x`가 된다.

  현재 코드는 `m_adder.v:7~23`에서 `ci[0]=cin`, 각 단계 `.cout(ci[i+1])`, 최종
  `cout=ci[W]`를 연결하고, `m_ALU.v:9~16`에서 이를 `add_c_wire`로 받아 `C_cout`에 전달한다.

- **[수정]** carry를 다음 경로로 끊김 없이 연결했다.

  ```text
  top cin → m_ALU cin → m_adder ci[0]
          → FA[0].cout → ... → FA[W-1].cout
          → m_adder cout → add_c_wire → C_cout → FSM C
  ```

- **[확인]** [`덧셈 문제해결.PNG`](../img_m_processer1/덧셈%20문제해결.PNG) 이후 정상 결과 파형에서
  `add_result`가 operand에 따라 결정되고, 최종 시나리오에서는 덧셈 결과가 더 이상 `x`가 아니다.

- **[교훈]** ripple-carry는 컨베이어벨트처럼 한 단계라도 끊기면 뒤가 전부 멈춘다. 최종 `sum`만 보지 말고
  `ci[0]`, 중간 `ci[i]`, `ci[W]`를 순서대로 올려 최초의 `x` 위치를 찾는다.

## E04 · N 플래그가 mode 변경 뒤에도 1로 유지됨

- **[파형]** [`N이 1이유지되는현상.PNG`](../img_m_processer1/N이%201이유지되는현상.PNG)

  ![N이 유지되는 파형](../img_m_processer1/N이%201이유지되는현상.PNG)

- **[증상]** mode가 감산 `01`을 지나 AND `10`, OR `11`로 바뀌었는데도 `N=1`이 계속 유지됐다.
  ALU 결과는 `8 → 4 → 2 → 6`으로 바뀌므로 N도 현재 연산 규칙에 따라 다시 결정돼야 했다.

- **[원인]** 수정 전 조합 블록에서 `N_cout`을 감산 분기에서만 대입하고 다른 mode에서 기본값을
  주지 않았거나, FSM 출력 N을 mode와 무관하게 이전 `N_cout`에 연결한 것으로 역추정된다.
  이런 구조는 감산 때의 1을 저장하는 latch를 만들거나, 의미 없는 연산에서도 감산 부호를 노출한다.

- **[수정]** ALU 조합 블록 시작에서 `N_cout=0`을 기본 대입하고(`m_ALU.v:27`), 감산 분기에서만
  `N_cout=sub_re[3]`으로 덮어쓴다. FSM 출력도 `mode==01`일 때만 N을 통과시키도록 했다
  (`m_FSM.v:66`).

- **[확인]** 최종 결과 파형에서 N은 해당 감산이 음수인 구간에만 의미를 가지며 다른 mode로 넘어가면
  0으로 복귀한다.

- **[교훈]** 조합 `always`에서는 모든 출력에 먼저 기본값을 준다. 플래그도 결과 데이터처럼
  **어떤 연산에서 유효한 신호인지** mode로 명확히 제한해야 한다.

## E05 · 입력쌍을 분리해 정상 경로와 overflow 경로 확인

### `a=4`, `b=1` — 정상 연산 전부 통과

![a=4 b=1 결과](../img_m_processer1/결과%20a=4,b=1.PNG)

| mode | 연산 | 결과 |
|---|---|---:|
| `00` | `4 + 1` | `5` |
| `01` | `4 - 1` | `3` |
| `10` | `4 & 1` | `0` |
| `11` | `4 | 1` | `5` |

### `a=3`, `b=5` — 덧셈 overflow

![a=3 b=5 결과](../img_m_processer1/결과%20a=3,b=5.PNG)

`3 + 5 = 8`은 4비트 signed 양수 범위를 넘어 `1000`이 된다. `V=1` 뒤 FSM이 ERROR로 이동해
후속 결과가 0이 되는 것을 확인했다.

### `a=2`, `b=10(4'b1010=-6)` — 감산 overflow

![a=2 b=10 결과](../img_m_processer1/결과%20a=2,b=10.PNG)

4비트 패턴 `1010`을 signed로 읽으면 -6이다. 덧셈 `2 + (-6) = -4 = 4'hC`는 정상이고,
감산 `2 - (-6) = 8`은 표현 범위를 넘어 `4'h8`과 `V=1`이 된다. 같은 비트 패턴도 unsigned 산술값과
signed overflow 해석이 다르다는 점을 확인한 케이스다.

## 재검토에서 확인한 사항

### R01 · register reset이 `mem[3]`을 초기화하지 않음

`m_register.v:12`의 루프가 `i<3`이라 `mem[0]~mem[2]`만 0으로 만들고 네 번째 칸 `mem[3]`은
초기화하지 않는다. 현재 테스트는 주소 0·1만 사용해 드러나지 않았지만 주소 3을 읽으면 `x`가 나올 수 있다.
네 칸 배열이면 범위는 `i<4` 또는 배열 크기를 파라미터로 묶어야 한다.

### R02 · `S_error`가 ALU에 연결되지 않음

`m_top_module.v`에서 FSM의 `S_error`는 암시적 wire로 생기지만 선언이 없고, `m_ALU` 인스턴스에는
`.S_error(S_error)` 연결이 빠져 있다. 따라서 ALU 입력 `S_error`가 floating 상태다. ERROR에서 결과를
0으로 만드는 책임을 명확히 하려면 신호를 선언하고 양쪽에 연결해야 한다.

### R03 · 파라미터 `W`를 선언했지만 4비트가 하드코딩됨

- `m_ALU.v:29`의 `result=4'b0000`
- `m_ALU.v:39`의 `N_cout=sub_re[3]`

`W=4`에서는 맞지만 폭을 바꾸면 깨진다. 각각 `'0`, `sub_re[W-1]`처럼 파라미터를 따라가야 한다.

### R04 · FSM의 ERROR와 DONE은 reset 전까지 빠져나오지 않음

현재 `ERROR→ERROR`, `DONE→DONE`인 terminal state다. 단발 계산기라면 의도일 수 있지만, 여러 계산을
연속 수행하려면 새 `start/ack` 규칙 또는 IDLE 복귀 조건이 필요하다. README에서는 단발 FSM인지
반복 가능한 프로세서인지 범위를 명확히 적어야 한다.

### R05 · 테스트벤치가 제어 신호를 `posedge`에서 바꿈

`mode`와 `cin`을 `@(posedge clk)` 직후 blocking 대입한다 (`mini_processer1_tb.v:56~64`). DUT의 FSM과
같은 시간 영역에서 경쟁할 수 있다. Project 8과 동일하게 자극은 에지 전에 준비하고, 에지 뒤에는
관찰만 하는 편이 안전하다.

### R06 · 자동 판정이 없음

결과 파형 세 장은 중요한 증거지만 사람이 직접 읽어야 한다. 정상 경로는 mode별 기대값,
오류 경로는 `V`와 ERROR 전이 시점을 자동 비교하면 이후 리팩터링의 회귀를 바로 잡을 수 있다.

## 교훈

1. FSM이 붙으면 현재 입력뿐 아니라 **직전 사이클이 만든 상태**까지 원인 후보에 넣는다.
2. carry chain은 시작점부터 끝점까지 계층 경계를 하나씩 추적한다.
3. 조합 출력과 플래그에는 기본값을 주어 latch와 이전 연산 잔류를 막는다.
4. 같은 4비트 값도 signed/unsigned 해석에 따라 overflow 의미가 달라진다.
5. 정상 케이스와 오류 유도 케이스를 분리해야 무엇을 검증했는지 명확해진다.
